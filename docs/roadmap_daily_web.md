## 一、项目定位

**Daily = 画布 + AI Agent**，是一个可部署的平台产品。

- **本质**：画布是前端交互页面，AI Agent 是核心能力，把 HTML 的所有优势发挥出来（动画、音乐、各方面能力）
- **产品形态**：部署到服务器上，通过网页访问，适配电脑和手机。用户部署 Daily 后，往自己服务器丢服务，给服务做 HTML 前端放 Daily 上
- **定位**：Daily 只是前端交互层，不管用户后端服务怎么跑
- **比赛策略**：3 天交稿（7月10号左右），不做残缺版，要做最好的效果，比赛只专心网页端
- **官方部署**：shadowshub.xyz/daily/，shadowshubs 将做成 Daily 的内置官方社区面板

## 四、详细阶段

### Phase 1 · 项目重构 + 三层画布模型

- **目标**：完成项目改名 Daily、清理 8 个内置 widget、建立三层画布模型结构，为后续所有阶段打好基础
- **主要功能点**：
  1. **项目改名**：将 AGENT.md、SPEC.md、package.json、index.html 等所有文档与配置中的 "Living Dashboard" 改为 "Daily"，统一项目代号
  2. **清理 8 个内置 widget**：删除 PdfViewer、MusicPlayer、FocusTimer、Sudoku、LatexQuiz、Calculator、AIAssistant、WebviewWidget 的注册与组件文件，保留 HtmlCanvasWidget（HTML 画布容器机制）+ 动态 widget 机制
  3. **三层画布模型结构**：在 Workspace.tsx 中建立背景层（最底）、组件层（中间）、弹出层（最上）的 DOM 结构与 z-index 体系，背景层始终存在不随相册缩放消失
  4. **背景层基础**：实现背景层的基础结构（图片/颜色/动画占位），为 Phase 5 的 AI 可控做准备
- **交付物**：
  - 更新后的 AGENT.md（项目名 Daily）
  - 清理后的 builtIn.tsx（仅保留 HtmlCanvasWidget + 动态 widget）
  - Workspace.tsx 三层 DOM 结构（background-layer / component-layer / popup-layer）
  - 背景层基础样式与占位渲染
  - 删除 8 个 widget 组件文件（PdfViewer.tsx / MusicPlayer.tsx / FocusTimer.tsx / Sudoku.tsx / LatexQuiz.tsx / Calculator.tsx / AIAssistant.tsx / WebviewWidgetFallback.tsx）
- **依赖**：无
- **可并行**：否（基础阶段，所有后续阶段依赖此阶段）

### Phase 2 · 两类组件 + 相册缩放

- **目标**：实现自由 HTML 组件（与 iframe widget 并列），完成相册三档缩放（normal/mini/icon）
- **主要功能点**：
  1. **自由 HTML 组件**：实现任意形状、自由移动（CSS 动画/JS 控制位置）、可跨 widget 边界、可配置全局覆盖或局部、与画布共享 DOM（无隔离）的组件类型；支持人操作和拖拽
  2. **组件类型注册**：在组件注册表中新增 freeHtml 类型，与 iframe widget（htmlCanvas）并列，AI 生成 HTML 时两种都支持，AI 自己判断放哪
  3. **相册缩放 - 滚轮吸附**：实现滚轮触发三档吸附（normal → mini → icon），放大时组件保持原样，缩小时动态优化
  4. **相册缩放 - 三档效果**：
     - normal：正常展示
     - mini：AI 选择的精简 HTML 形态（本质是一个很小的 HTML，不是简单缩放）
     - icon：AI 画的 HTML 图标（不是固定方形，可以是圆形或任意形状）；最小档位卸载 iframe 省性能
  5. **缩放规则**：大的先缩小（确保整体协调统一），无论自由组件还是 iframe widget 都按大小决定怎么缩放
  6. **档位触发值**：用户可调（如 zoom>2.0 为最大，zoom<0.4 为最小）
  7. **虚拟化**：中等档位只渲染视口内 widget，最小档位卸载 iframe 只显图标
- **交付物**：
  - FreeHtmlComponent 组件（自由 HTML 组件实现）
  - 组件注册表新增 freeHtml 类型
  - 相册缩放状态机（normal/mini/icon 三档）
  - 滚轮吸附交互逻辑
  - 虚拟化渲染逻辑
  - 档位触发值设置 UI
- **依赖**：Phase 1（三层画布模型）
- **可并行**：是（与 Phase 3、Phase 4 并行）

### Phase 3 · AI 对话重构 + 工具开关

- **目标**：用浮球 + 底部任务栏替换矩形 AI 助手 widget，实现 AI 工具设置页开关控制
- **主要功能点**：
  1. **浮球形态**：小圆形组件始终置顶，哪怕 HTML 占满全屏也在最上层
  2. **底部任务栏形态**：椭圆形发送框（靠右侧，不放在中间）+ 上方对话历史气泡展示（类似微信聊天气泡，适合 AI 对话场景）
  3. **两种形态切换**：支持浮球与底部任务栏切换（底部任务栏可能影响 HTML 查看，所以支持切换）
  4. **AI 对话功能替换**：Phase 1 已删除 AIAssistant widget 注册与组件文件，本阶段用浮球/底部任务栏形态替换原 AI 对话功能，迁移现有 WS 流式对话、多会话管理、ask_user、permission_request、双 watchdog 等能力到新形态
  5. **AI 工具设置页开关**：在设置页增加文件系统工具开关（read/write/edit/bash/grep/find/ls），默认关闭，用户手动开启
  6. **PI 原本工具开放**：将 PI agent 原本 7 个工具（read/bash/edit/write/grep/find/ls）做成可选启用，在服务端 Node.js 跑加沙箱
- **交付物**：
  - FloatingOrb 组件（浮球，始终置顶）
  - BottomTaskbar 组件（底部任务栏 + 对话气泡）
  - 形态切换逻辑
  - 设置页 AI 工具开关 UI
  - 后端文件系统工具开关与沙箱
  - 现有 AI 对话能力迁移到新形态（WS 流式、多会话、watchdog 等）
- **依赖**：Phase 1（组件清理）
- **可并行**：是（与 Phase 2、Phase 4 并行）

### Phase 4 · 多用户系统 + 面板多建

- **目标**：自建完整用户系统（注册+登录+角色），实现个人面板可多建 + 社区面板可多建
- **主要功能点**：
  1. **用户系统**：新增 users 表 + 注册 + 登录 + 角色（admin/member），跟 shadowshubs 用户系统分开
  2. **管理员机制**：部署者 = 该实例管理员（谁部署谁就是老大），需要管理员名单机制方便开发者添加管理员
  3. **管理员功能**：设置全局组件（所有用户可见）、用户管理（封禁/角色分配）、AI 配置管理（API Key/模型/工具权限）、工具/搜索引擎配置
  4. **个人面板多建**：支持创建多个个人面板（学习/生活/休闲等），每个面板有独立布局
  5. **社区面板多建**：管理员可创建多个社区面板（按主题分区，如游戏社区/学习社区）
  6. **社区面板内容**：管理员设置的全局组件（所有用户可见）+ 用户自己的个人组件（仅自己可见），无投稿/审核功能
  7. **社区面板创建弹窗**：创建社区面板时弹出登录窗口（弹出层 HTML widget），登录成功后关闭弹出层
- **交付物**：
  - users 数据库表 + 注册/登录 API
  - 角色权限系统（admin/member）
  - 管理员后台页面（用户管理、AI 配置、全局组件设置）
  - 个人面板多建 UI 与 API
  - 社区面板多建 UI 与 API
  - 社区面板创建弹窗（弹出层）
- **依赖**：Phase 1（基础结构）
- **可并行**：是（与 Phase 2、Phase 3 并行）

### Phase 5 · 背景层 + 弹出层 + 组件导入

- **目标**：完成背景层 AI 可控、弹出层全功能触发、组件导入（手动上传 + API）
- **主要功能点**：
  1. **背景层 AI 可控**：AI 可控画布属性，AI 可上传图片当背景，AI 可加特效（下雨等），AI 可在背景某处放基础组件（时钟显示等）；背景上的东西始终存在不随相册缩放消失
  2. **弹出层全功能触发**：
     - 进入时触发（第一次打开面板时）
     - 条件触发（未登录时、登录失效时、打开某东西时）
     - 定时触发（每过一段时间）
     - 手动触发（用户/AI 主动调用）
  3. **弹出层关闭条件**：登录成功后自动关闭、用户点击关闭、定时关闭、AI 主动关闭；支持单次弹出/可重复弹出；多个弹出层可叠加
  4. **组件导入 - 手动上传按钮**：画布上提供"上传组件"按钮，支持拖拽 HTML 文件或粘贴 HTML 代码
  5. **组件导入 - API 接口上传**：提供 REST API，开发者可通过 API 上传组件
  6. **导入内容**：用户在本地自己开发，把开发的组件上传到 Daily 服务上部署，可上传很多组件、代码和服务
- **交付物**：
  - 背景层 AI 控制工具（set_background/upload_image/add_effect/place_basic_component）
  - 弹出层触发引擎（4 种触发模式）
  - 弹出层管理 UI（创建/关闭/叠加）
  - 画布上传组件按钮（拖拽 + 粘贴）
  - 组件上传 REST API
  - 上传组件存储与渲染
- **依赖**：Phase 1（三层模型）、Phase 2（两类组件类型）
- **可并行**：否（Phase 5 后半段可与 Phase 6 并行）

### Phase 6 · 社区功能 + 开发者文档

- **目标**：实现官方社区列表与联邦式社区，完成开发者文档与 AGENT.md 索引
- **主要功能点**：
  1. **社区模型**：一个 Daily 部署 = 一个平台实例 = 一个社区，部署者 = 管理员，管理员可创建多个社区面板
  2. **联邦式社区**：每个社区独立用户系统，各社区独立注册登录，用户在 A 社区注册后不能在 B 社区投稿必须各自注册，Daily 作为客户端聚合展示多个社区
  3. **社区发现**：官方社区列表（开发者提交申请，默认通过），用户从官方列表选择添加或手动输入地址
  4. **社区连接**：创建社群面板时输入内容（社区地址/API），连接到外部社群，连接涉及用户管理、用户筛选
  5. **社区功能实现**：功能拆解 + 本地实现（不嵌入 shadowshubs 前端），把 shadowshubs 的能力拆成 widget，在 Daily 侧自己实现
  6. **开发者文档**：新增专门文档（组件规范/API/部署指南/端到端流程），放在 docs/ 下，后面放到网站上，在 AGENT.md 里做索引
  7. **文档内容**：组件开发规范（HTML 组件接口、约束、能力）、API 文档（上传组件、管理面板、配置平台）、部署指南（部署 Daily、配置、搭建社区）、端到端流程（本地开发组件 → 上传 → 部署 → 使用）
- **交付物**：
  - 官方社区列表 API + UI
  - 联邦式社区连接逻辑
  - 社区聚合展示
  - docs/developer-guide.md 开发者文档
  - AGENT.md 索引更新
  - 组件开发规范文档
  - API 文档
  - 部署指南
- **依赖**：Phase 4（多用户系统）
- **可并行**：是（与 Phase 5 后半段并行）

## 五、并行策略

### 可并行阶段

| 并行组 | 阶段 | 前置条件 | 并行原因 |
|--------|------|---------|---------|
| 并行组 A | Phase 2、3、4 | Phase 1 完成 | 三者改动的代码区域完全不重叠 |

#### 并行组 A 详细说明（Phase 2 ∥ Phase 3 ∥ Phase 4）

- **Phase 2（两类组件 + 相册缩放）**：改动 `Workspace.tsx` 画布层、组件注册表、新增 FreeHtmlComponent，主要在前端画布渲染层
- **Phase 3（AI 对话重构 + 工具开关）**：改动 AI 对话组件（FloatingOrb/BottomTaskbar）、设置页、后端工具开关，主要在 AI 交互层与后端工具层
- **Phase 4（多用户 + 面板多建）**：改动后端 users 表、认证 API、面板管理 API，主要在后端用户系统与面板管理

三者代码区域不重叠，可安全并行。并行时注意：
- Phase 2 与 Phase 3 都可能涉及 Workspace.tsx，需协调：Phase 2 改组件层渲染，Phase 3 改浮球/任务栏挂载点（弹出层），分工明确
- Phase 4 纯后端 + 少量前端认证 UI，与前两者无冲突

### 不可并行阶段

| 阶段 | 原因 |
|------|------|
| Phase 1 | 基础阶段，所有后续阶段依赖三层模型与清理后的代码 |
| Phase 5 | 依赖 Phase 1 的三层模型 + Phase 2 的两类组件类型 |
| Phase 6 | 依赖 Phase 4 的多用户系统 |
| Phase 7 | 收尾整合阶段，依赖 Phase 6 的社区功能 |

### 半并行阶段

- **Phase 5 后半段 ∥ Phase 6**：Phase 5 前半段（背景层 AI 可控）完成后，组件导入部分可与 Phase 6（社区功能 + 开发者文档）并行，因为组件导入与社区功能无强依赖

## 七、风险与注意事项

### 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 自由 HTML 组件与画布共享 DOM 导致污染 | 组件 JS 可能影响画布状态 | 严格约束自由组件能力，提供沙箱化建议；AI 生成的自由组件需通过审核机制 |
| 相册缩放 mini/icon 档需 AI 生成精简 HTML | AI 生成质量不稳定 | 预置 fallback 策略（AI 生成失败时用简单缩放降级） |
| 多用户系统改造影响现有单密码登录 | 现有用户数据迁移 | 保留单密码模式作为 fallback，新系统兼容旧数据 |
| 联邦式社区跨实例用户系统复杂 | 跨社区认证与数据同步 | MVP 阶段各社区独立注册，不做统一身份 |
| 18 个 browser_* 工具不可用 | AI 能力受限 | 不在本次 roadmap 范围，web 端用其他工具替代 |

### 依赖风险

| 风险 | 缓解措施 |
|------|---------|
| Phase 1 延迟导致后续全部延迟 | Phase 1 范围严格控制，只做改名 + 清理 + 三层结构，不扩展 |
| Phase 5 依赖 Phase 2 的两类组件 | Phase 2 优先完成自由 HTML 组件，Phase 5 可提前介入设计 |
| shadowshubs 整合依赖社区功能 | Phase 7 只做框架，详细整合后续迭代 |

### 时间风险

| 风险 | 缓解措施 |
|------|---------|
| 3 天完成 7 个阶段时间紧张 | 充分利用并行组 A（Phase 2/3/4 三路并行），Day 2 是关键 |
| 比赛交稿日期可能提前 | 降级策略保证 Phase 1-5 完整，Phase 6/7 可精简 |
| 调试时间不足 | 每个 Phase 完成后立即验证，不做完整对抗审查（比赛期间省时间，赛后补） |

### 注意事项

- **项目名必须叫 Daily**，所有文档、代码、配置统一使用，不能出现 Living Dashboard
- **比赛期间不做完整对抗审查**，但每个 Phase 必须有运行时验证（设计文档 §17.3 要求）
- **不下载到 C 盘**，所有依赖与构建产物放其他盘（设计文档 §17.1）
- **必须用 git 做版本管理**，每个 Phase 完成后 commit（设计文档 §17.1）
- **尽可能使用 TypeScript**（设计文档 §17.1）
- **不能说"基本合格、条件通过"**，要么完全合格要么不合格（设计文档 §17.1）
